1. Resumen ejecutivo

Atlas es un asistente de IA con control sobre tu PC Windows (web browser, CorelDRAW, archivos, ventanas, teclado/mouse) que además se observa a sí mismo: registra tu actividad, clasifica si tu tiempo fue productivo o "fugado", evalúa su propia salud y decide dinámicamente qué modelo de IA usar según la tarea (routing inteligente entre varios proveedores).

Se compone de 13+ scripts Python que actúan como servidores MCP (Model Context Protocol) y servidores HTTP, más tareas de Windows que los levantan automáticamente al iniciar sesión. El núcleo es un SQLite (memory_data/state/memory.db) que centraliza eventos, sesiones, notas y decisiones.

2. Qué es Atlas (identidad y propósito)

Propósito

  • Ser un agente con "manos en el PC": puede navegar la web, manipular CorelDRAW (diseño vectorial POD), controlar ventanas/teclado/mouse, y ejecutar scripts — siempre gobernado por un modo guardián con niveles de riesgo.
  • Memoria persistente: guarda notas, decisiones, hechos y sesiones en una bóveda Obsidian + índice FTS5, con grafo de conocimiento.
  • Auto-observación (Foco): el daemon de actividad captura la app activa, clasifica cada evento como productivo/distracción y calcula % de foco diario.
  • Auto-gestión de modelos (Orquestador): detecta en vivo qué proveedores responden (OmniRoute, 9Router, Ollama) y qué modelos existen de verdad; sugiere el mejor modelo por tarea sin inventar.
  • Auto-reparación: semáforo de salud (verde/amarillo/rojo), logging estructurado JSON, monitoreo de errores, backups automáticos y rotación de secretos.

4. Componentes / módulos

4.1 Núcleo de datos — mcp_memory_server.py

FunciónDetalle
Bóvedamemory_data/vault/ — notas Obsidian con frontmatter: notes/ decisions/ facts/ sessions/ preferences/
Base de datosmemory_data/state/memory.db — SQLite con tablas events (780+ filas), sessions, FTS5 para búsqueda
Grafosvault/global/graph.json, vault/desplegar/graph.json — grafo de conocimiento (frontmatter + wikilinks)
Daemon inboxgit hooks (post-commit) escriben eventos a memory_data/inbox/; event_ingest los drena a SQLite
Backups--cli backup genera zip en memory_data/backup/; tarea AtlasBackup diaria
Secretosstate/secret_rotation.json — calendario de rotación cada 90 días

4.2 Observación de actividad — atlas_activity.py (daemon + bandeja)

  • Captura la ventana activa cada N segundos (default 10s) y escribe eventos con app, window_title, category, monetizable, duration_seconds.
  • Escribe state/daemon.heartbeat (PID, status, last_tick, uptime, foco_mode) — lo consumen health y dashboard.
  • Trae bandeja de sistema (pystray). Con --no-tray corre como servicio para servidor.
  • Rate limiting: máx 6 eventos/min hacia inbox para no inundar.

4.3 Foco / disciplina — atlas_foco.py + foco_rules.py

  • Clasifica apps por categorías (dev, research, social, etc.) con reglas en state/foco_rules.json.
  • Modos: off (solo medir), soft (avisos con presupuesto), strict (avisos agresivos).
  • foco_daily_summary → % de foco del día, top distracciones. backfill reclasifica eventos históricos.
  • Overrides manuales: foco_override(app, categoria) fuerza la clasificación de un ejecutable.

4.4 Salud / semáforo — atlas_health.py

  • health_report() → status green/yellow/red + checks detallados (daemon, omniroute, ollama, venv, state, configs, inbox).
  • Verificación real por API: omniroute/ollama se comprueban con GET a su API, no solo el puerto (evita falsos positivos).
  • HTTP server opcional --http 4102; el dashboard lo consume vía atlas_web_server.

4.5 Orquestador de modelos — atlas_orchestrator.py CLAVE

  • Detección viva: consulta la API real de cada provider (/v1/models en OmniRoute/9Router, /api/tags en Ollama) con caché de 15s. Puerto abierto + API que no responde = NO usable.
  • Pool real: solo ofrece modelos que existen de verdad (OmniRoute expone 260; curar lista: best-coding/reasoning/fast/chat/vision).
  • Routing por tarea: analyze(task) → best_model_for(task) con mapa de capacidades (state/model_capabilities.json) + heurística por nombre si el modelo es desconocido.
  • Circuit breaker: 3 fallos consecutivos → cooldown 300s → degrade y prueba el siguiente provider (fallback chain omniroute → 9router → ollama).
  • Decisiones registradas en state/routing_log.json; tools register_error/register_success para retroalimentar.
  • Regla dorada: nunca sugerir modelo sin la capacidad requerida (ej. visión) — avisa y recomienda cambiar en vez de trabajar a ciegas.
  • MCP + CLI (--cli) + HTTP (--http 4103).

4.6 Dashboard real — atlas_web_server.py NUEVO

  • Un solo servidor en :4100 que sirve el HTML (atlas_web/dashboard.html) y una API unificada con datos reales de memory.db.
  • Endpoints: /api/overview (daemon, events_total, sessions_total, last_tick), /api/top-apps (top 12 apps 24h), /api/foco, /api/health, /api/orchestrator, /api/modelo.
  • Reutiliza la lógica de foco/health/orquestador importándolos (sin duplicar código). Elimina la dependencia de opencode serve + 3 servers.
  • Autostart: tarea AtlasWeb (ONLOGON) + start_atlas_web.vbs.

4.7 Chat flotante — atlas_chat.py PROBLEMA

  • Arranca opencode serve headless en :4096 y abre una ventana pywebview (WebView2) frameless que apunta a una sesión del server.
  • Modelo hardcodeado: omniroute/auto/best-chat (existe en el catálogo real).
  • Falla conocida: no inicia al arrancar el sistema (ver flujo 3). El 13/08 16:52 la tarea corrió (resultado 0) pero no escribió logs y :4096 quedó sin server.

4.8 Búsqueda web — atlas_search.py

  • Servidor MCP con web_search (DuckDuckGo → SearXNG → DDG HTML, cadena de respaldo) y web_research (investigación multi-ronda que guarda informe en la bóveda).

4.9 Guardián — atlas_guardian.py

  • Niveles relax / guard / strict. Valida operaciones (run_command, process_kill, file_delete, registry_write) → allowed/requires_confirmation.
  • Config: state/guardian.json; listas blancas de binarios/procesos. Integrado también dentro de mcp_windows_server.py (candidatos de config vía env ATLAS_GUARDIAN_CONFIG).

4.10 Monitoreo/errores — atlas_monitor.py + atlas_log.py

  • atlas_log: logging JSON estructurado (logs/*.log): ts, level, source, msg, campos extra.
  • atlas_monitor: logs/errors.jsonl + state/errors.db (frecuencia); rate limiter de daemon.

4.11 MCP consolidados — mcp_windows/

  • mcp_windows_server.py (71KB): ventanas, teclado, mouse, archivos, portapapeles, wifi, docx. Gobernado por guardian.
  • mcp_corel_server.py (57KB): CorelDRAW — crear documentos, shapes, curvas Bezier, booleanas, texturas, exportar PNG/JPG/PDF, macros VBA (POD Suite).
  • mcp_playwright_visual_server.py (23KB): Chromium real para navegación/clicks/auditoría visual determinista.
  • Consolidados dentro del repo (antes en repo hermano E:\MCP\mcp-windows-ai) para portabilidad.

10. Qué hace y qué NO hace

✅ SÍ hace

  • Ejecutar scripts y comandos con permiso del guardian (nivel por defecto guard: destructivo pide confirmación).
  • Navegar la web con navegador real (Playwright) y automatizar webs (ej. configurar n8n).
  • Diseñar en CorelDRAW (vectorial POD: shapes, curvas, texturas, exportar PNG/JPG/PDF, macros VBA).
  • Controlar ventanas/teclado/mouse/archivos/portapapeles/docx.
  • Recordar contexto entre sesiones (bóveda + grafos + FTS5).
  • Medir foco diario, clasificar apps, avisar distracciones.
  • Elegir modelo por tarea según proveedores REALMENTE activos.
  • Reportar salud del sistema y hacer backup/restore.

❌ NO hace (aún)

  • NO cambia el modelo en runtime por sí solo: el orquestador sugiere/avisa, pero el switch requiere acción externa.
  • NO inicia la ventana flotante de forma fiable (AtlasChat roto en arranque).
  • NO auto-inicia OmniRoute como tarea; arranca por OS/manual.
  • NO usa 9Router (no instalado) — por tanto el fallback chain omniroute→9router→ollama está incompleto en la práctica.
  • NO conecta el dashboard a un remote/git ni tiene origin configurado.
  • NO tiene métricas de uso/costo por modelo.
  • NO implementa F4 (dinero), F5 (tutor), F6 (horizonte).
  • NO sincroniza model_capabilities.json automáticamente con el catálogo real (datos muertos detectados, ej. best-research).

13. Cómo portar a otro PC

  1. Clonar/copiar el repo a la nueva máquina.
  2. powershell -ExecutionPolicy Bypass -File setup.ps1 — crea .venv, instala deps, detecta providers (omniroute/9router), sustituye rutas en opencode.jsonc y registra tareas.
  3. El repo es autocontenido tras consolidar mcp_windows/ (ya no depende del repo hermano).
  4. Instalar runtime: Node (opencode, omniroute, 9router), Python .venv, WebView2, CorelDRAW (si se usará).
  5. Verificar con check.ps1 (→ TODO OK) y el dashboard :4100.
