Atlas — SPEC C1 · Capa de Ejecución Profesional

Contrato de implementación · v1.0 · 14/08/2026 · Dirigido a: IA ejecutora / programador
Regla de lectura: cada REQ es bloqueante. Prohibido cerrar con "debería funcionar". Toda afirmación requiere evidencia (test, log, captura, comando).

01 · Propósito y norte

Atlas ejecuta la intención del usuario, sobre los programas del usuario, con calidad profesional verificable.

  • No asume programas: opera el navegador/app que el usuario indique (registro de programas).
  • No ejecuta la frase literal: construye orden de trabajo (objetivo, alcance, profundidad, entregable, criterios).
  • No entrega "informes de preparatoria": estándar profesional de 6 bloques, maquetación con oficio, evidencia real.
  • No declara éxito sin evidencia: loop ejecutar → verificar → corregir; limitaciones honestas.
  • Todo entregable se guarda, se publica en dashboard y se versiona.

03 · Glosario

  • Orden de trabajo: interpretación estructurada de la petición antes de ejecutar.
  • Nivel (L0–L3): profundidad de investigación/entrega con criterios medibles.
  • Runbook: procedimiento verificado guardado en bóveda, reutilizable, con versión de programa.
  • Crítico: pase de auditoría con modelo distinto antes de entregar.
  • Checkpoint: estado reanudable de tarea larga en state/tasks/<id>.json.
  • Exemplar: entregable calificado "así sí" por el usuario; referencia few-shot.

04 · Skills nuevas (6) — contenido detallado

skill: ejecucion-verificada (MASTER)

description: "Usar al ejecutar CUALQUIER tarea que modifique o configure programas, archivos o el PC del usuario. Obligatoria antes de tocar UI, apps o configs."

  1. Construir orden de trabajo (plantilla §17). Si ambigüedad crítica → preguntar UNA vez.
  2. Leer preferences/programas.md; si el programa no está registrado → preguntar y recordar.
  3. Buscar runbook aplicable (skill runbooks). Si existe → seguirlo; si no → planificar pasos con criterio de éxito POR PASO.
  4. Ejecutar UN paso. Verificar con cascada: API/CLI → UIA (read_ui_state) → OCR/captura+visión → teclado/mouse.
  5. Fallo → reintentar con alternativa (máx 2). Segundo fallo → checkpoint + reportar con evidencia, nunca éxito falso.
  6. Diálogo nativo detectado (UIA/OCR) → operarlo con teclado/mouse vía windows MCP.
  7. Verificación final contra criterios de aceptación de la orden.
  8. Si el procedimiento es nuevo y exitoso → guardar runbook.
  9. Ritual de entrega (skill entrega).
skill: informe-profesional

description: "Usar cuando el usuario pida informe, reporte, análisis, comparativa o documento. Aplica estándar de 6 bloques y maquetación profesional."

  1. Orden de trabajo + nivel (default del usuario: L2/L3).
  2. Estructura obligatoria (§08). Resumen ejecutivo con conclusiones PRIMERO.
  3. Visualización con oficio: tabla para comparativas, SVG inline para series, timeline para secuencias. Autonomía de forma, estándar de fondo.
  4. HTML single-file sin dependencias externas (abrible offline) · DOCX vía windows MCP si el usuario lo prefiere · MD en bóveda siempre.
  5. Pase crítico (skill critico) ANTES de mostrar.
  6. Versionado -v1/-v2 si hay feedback; exemplar si el usuario lo califica "así sí".
skill: investigacion-exhaustiva

description: "Usar para búsquedas exhaustivas, estudios profundos, tendencias, análisis de mercado. Protocolo L3."

  1. Descomponer en 3-6 sub-preguntas.
  2. 3-4 rondas: web_search + web_research + fuentes académicas (CrossRef/arXiv).
  3. Jerarquía de fuentes (§15); ≥3 por afirmación clave; fecha de captura y cita textual con link.
  4. Contradicciones entre fuentes → sección explícita, no se ocultan.
  5. Datos vs opinión separados. Entregar vía informe-profesional.
skill: runbooks

description: "Usar ANTES de ejecutar procedimientos repetidos (instalar extensión, exportar diseño, publicar informe) y DESPUÉS de uno exitoso nuevo."

  • Formato: vault/<proyecto>/runbooks/<nombre>.md con pasos, selectores/UIA names, verificaciones, versión del programa, fecha última verificación.
  • Ciclo: verificado → reusado → stale si cambia versión del programa → re-verificar antes de usar.
skill: critico

description: "Usar ANTES de entregar cualquier entregable. Pase de auditoría con modelo DISTINTO al generador."

  • Checklist §09 contra criterios de aceptación de la orden. Detecta placeholders, invención, huecos, maquetación pobre. Exige corrección ANTES de mostrar al usuario.
skill: entrega

description: "Usar al finalizar toda tarea con entregable. Ritual de persistencia y presentación."

  1. Guardar en vault/outputs/ + publish_report (dashboard /api/informes).
  2. Entrada en grafo + resumen en sesión.
  3. Mensaje final: "listo · publicado en dashboard · archivado · cubrí A/B/C · excluí D por alcance · limitaciones: X · fuentes en anexo".

08 · Estándar de entregable profesional

  1. Cabecera: título, fecha, orden original literal, alcance, nivel, costo/tiempo.
  2. Resumen ejecutivo: conclusiones PRIMERO, 5-10 líneas, cero relleno.
  3. Hallazgos: por tema; tablas/comparativas; datos con fuente; SVG inline donde comunique mejor.
  4. Evidencia: fuentes jerarquizadas, links, fecha captura, citas textuales.
  5. Conclusiones y recomendaciones: accionables, priorizadas P1/P2/P3.
  6. Anexos + Limitaciones: datos crudos, glosario, y "no verificado" con evidencia del intento (honestidad > perfección).

Estilo: datos > adjetivos · frases cortas · prohibido relleno ("en el mundo dinámico de hoy") · números con fuente · tablas para comparar.
Formatos: HTML single-file offline (primario) · DOCX (alternativo) · MD bóveda (siempre). Nunca .txt plano salvo petición.
Plantillas + exemplars: vault/global/templates/ + entregables calificados "así sí" como referencia few-shot.

09 · Crítico y auto-auditoría

  • Checklist: ¿responde la orden punto por punto? · ¿resumen ejecutivo con conclusiones primero? · ¿toda afirmación con fuente? · ¿sin placeholders/TODO/invención? · ¿legible para quien no vio el proceso? · ¿offline? · ¿guardado+publicado? · ¿limitaciones honestas?
  • Modelo crítico DISTINTO al generador. Corrige ANTES de mostrar.
  • Feedback del usuario ("quedó flojo") → type=feedback en bóveda → ajusta style_profile.md (REQ-C12).

10 · Persistencia y ritual de entrega

Todo entregable: vault/outputs/ + grafo + /api/informes + resumen en chat (§04 entrega). Versionado -v1/-v2. Nada se entrega solo por chat.

11 · Runbooks

Ciclo: verificado → reusado → stale → re-verificado. Frontmatter: programa, version, ultima_verificacion, pasos, verificaciones.

12 · Checkpoints

Tareas >N pasos: state/tasks/<id>.json (pasos, estado, evidencia). Reanudable tras caída (task_resume). Integra con memory_session_recover.

13 · Seguridad en entregables

Redactor de secretos + datos personales ANTES de publicar o enviar a modelo cloud (REQ-C14). Entregables con sensibles → solo local.

14 · Evals (medir el % real)

Casos mensuales con rúbrica: (1) instalar extensión en navegador del usuario · (2) informe L3 de 5 fuentes · (3) diseño Corel + export · (4) config con diálogo nativo · (5) comparativa con tabla. Rúbrica: orden entendida · criterios % · evidencia · maquetación (crítico) · costo/tiempo. Tarea programada mensual + panel en dashboard.

15 · Fuentes

Jerarquía: oficial > académica > prensa > foro. Contradicciones → sección explícita. Datos vs opinión separados.

19 · Definición de terminado C1

  • 6 skills instaladas y activadas por description sin invocación manual.
  • Tools C10 operativas sobre el navegador real del usuario.
  • /api/informes sirviendo reportes reales.
  • Switch runtime probado (routing_log).
  • 3 entregables calificados "profesional" por el usuario.
  • Crítico detecta error sembrado (test).
  • 2 runbooks verificados · evals programados · style_profile activo.
