03 Puntos donde puede romperse

Haz clic en cada punto para ver la mitigación.

Integración TradingView (export de trades por demo varía; scraping se rompe)F5
Mitigación: adaptador externo de import CSV → normalizado. Nunca scraping frágil como núcleo.
Datos de ingresos dependen de que tú los alimentesF4
Mitigación: import CSV (banco/Stripe) + entrada manual rápida; el agente lo solicita proactivamente.
Clasificar app como distracción con heurísticas → falsos positivosF3
Mitigación: umbrales ajustables + reglas en activity_rules.json editable, no en código.
Post-commit hook falla silencioso (PATH / venv / timeout)F1
Mitigación: el hook solo escribe en inbox/; memory_event_ingest drena a SQLite; memory_health detecta backlog no procesado.
Sesiones huérfanas si se cierra la terminal sin /guardarF1
Mitigación: memory_session_recover al iniciar detecta sesiones abiertas y las marca como incompletas.
A→B/C: la UI A se acopla al navegadorF2
Mitigación: la UI A es HTML/JS puro sobre API opencode serve; B/C solo cambian el contenedor.
Bóveda crece sin control → contexto saturadoF1
Mitigación: MEMORY.md = índice · memory_gc · summary con presupuesto de tokens.

04 Reglas del roadmap (anti-ruptura)

  • F1 nunca se replantea al llegar a F5 — schema events, bóveda, permisos e identidad nacen "finales".
  • Cada integración externa (TradingView, banco, web) = adaptador reemplazable, nunca lógica en el núcleo.
  • Graphify siempre opcional — el sistema funciona sin él.
  • Lo que no está en la bóveda no existe — toda decisión que Atlas recuerde pasa por Obsidian.
